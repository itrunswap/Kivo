# Kivo 历史 CLI 与 Web 测试报告

说明：v0.2.4～v0.2.6 测试时产品名为 ProxyPilot，本文保留历史版本、命令与文件名，
不将旧版实测结果改写成 Kivo v0.2.7 的新验收结果。本地脱敏证据位于忽略目录，
不随仓库或发行包公开。正式仓库模块现已统一为 `github.com/itrunswap/Kivo`。

测试日期：2026-10-06。修复交付版本：v0.2.4。

后续 v0.2.5、v0.2.6 的回归记录位于文末。下文 v0.2.4 的“不自动设置/恢复系统代理”属于
当时版本边界，v0.2.6 已新增自动接管和恢复；不能把旧版真实联网记录当作新版实机验收。

共保留 183 条阶段性真实 CLI 命令记录（包含修复前、复测及预期失败），另有交互
键盘与浏览器操作。覆盖主要命令组及关键路径，但不等于所有参数组合、平台和网络
条件的穷举验收。

## 结论

已有 AES 加密订阅可以解密，直连和固定 PROXY 出站均成功更新，Mihomo 解析出
218 个代理条目。HTTP 与 SOCKS5 混合入口完成真实 HTTPS 请求，Google / Cloudflare
在规则模式和全局模式下均有成功记录；全局出口经控制接口与实际流量共同确认。

并非所有节点稳定可用。不同时间的批量检查分别出现 195/23、192/26、188/30
（通过/未通过），单个目标也出现过超时或 TLS 失败，随后复测通过。最后一组 CLI
批量检查为 188 个通过、30 个未通过。数量包括订阅商返回的提醒占位节点，
不等于可用节点数量，不代表带宽或持续稳定性。

**代理服务可用，不等于浏览器已经接入。** 测试时系统 HTTPS 代理未指向本测试实例，
期间也观察到 PAC 状态；测试没有更改系统代理、PAC 或系统路由。Web 的“检测外网”
由服务主机通过真实 Mihomo 出口发送 HTTPS 请求，不能据此宣称用户所有浏览器流量
已经经过本程序。

浏览器打开 Google 的导航调用超时；恢复连接时标签标题为 Google、URL 已跳转
`https://www.google.com.hk/`，但未完成该页内容与出口验证。这一结果不用于证明浏览器
经本程序上网。明确指定本地 HTTP 代理的 Google HTTPS 请求收到 302，SOCKS5 代理
访问 Cloudflare 收到 200；CLI 两种路由模式的两个检测目标均有完整通过记录。

## 发现并修复的问题

| 问题 | 原因及处理 |
| --- | --- |
| 全局模式仍可能直连 | Mihomo GLOBAL 是独立选择组，仅切换 mode 不改变默认 DIRECT；切换、启动及热重载时明确选择 PROXY |
| 保存节点没有可靠恢复 | 依赖 Mihomo cache.db；启动时应用持久化选择，节点被删除时记录回退原因 |
| 测速混入 DIRECT 并漏报失败 | 直接展示内核返回 map；按已加载节点归一化，补充失败 0，输出成功/失败数量 |
| 节点序号会变化 | 按延迟排序且存在 map 遍历不确定性；改为按完整名称排序，缓存列表使用相同顺序 |
| 未测节点被称为可用 | alive 默认值可能为 true；增加 tested 状态及明确检查文案 |
| Windows 同版本在线安装/导入失败 | 运行中的 exe 被锁定；下载与验证后再停止替换，导入先验证旁路文件 |
| Windows 路径丢反斜杠 | 解析器把所有反斜杠当转义；识别盘符/UNC 路径，保留分隔符 |
| CLI 在 Token 修改后失联 | 长驻会话缓存旧 Token；命令与状态刷新边界读取最新本地配置 |
| 订阅路径凭据泄露 | 只隐藏 query；追加路径段、用户信息及片段脱敏 |
| 路由页空白 | profile.groups 为 null 时读取 length 报错；容忍空切片并显示空组提示 |
| 窄终端/页面信息丢失 | CLI 表格按字符而非显示列填充，Web 窄屏隐藏检查状态；使用显示列布局并保留状态与延迟 |
| 错误参数仍提示成功 | sub add/edit 忽略未知选项；校验选项及多余位置参数，错拼直接拒绝 |
| 空规则组提示“1-0” | 空列表沿用序号范围错误；改为明确提示暂无规则 |
| 刷新和旧测速不一致 | 页面刷新仅更新概览，旧延迟覆盖新历史；刷新当前视图，重新读取节点时清理旧测速值 |

补充了端口监听就绪检查：真实内核回环复测发现热重载返回和监听器恢复存在短暂间隔，
不能把控制接口就绪等同于代理端口就绪。修复后真实内核集成测试连续五次通过。

## 下载故障的实测原因与用法

当前网络对官方 GitHub Release 的直接下载发生超时，100 秒测试预算内未完成。
通过已运行的 Mihomo 代理下载成功：v1.19.31 约 10.1 秒（21.4 MiB），
v1.19.30 约 8.5 秒（17.7 MiB）。这不是解密密码错误，也不是重试次数不足。

日常实例在默认代理端口 17890 下可使用：

```text
/core start
/proxy check
/config download-proxy http://127.0.0.1:17890
/core install v1.19.31
```

若尚无可运行的内核，不能指望使用它自身的代理下载；应使用另一可用 HTTP 代理，
或下载官方压缩包后 `/core import "C:\Downloads\官方文件名.zip"`。
安装器的空代理/system 表示使用环境 HTTP_PROXY/HTTPS_PROXY，**不是读取 Windows
手动代理/PAC，也不是强制直连**；`download-proxy direct` 当前不受支持。

## 仍需注意及未验证项

1. 程序目前不自动设置或恢复系统代理。浏览器需要按 `/proxy setup` 接入；测试没有为
   Google 浏览器页临时修改系统代理，因此不宣称浏览器自身出口已被本程序接管。
2. Web 尚未覆盖 CLI 的全部高级管理：已有订阅编辑/移动、规则组与路由配置创建、
   离线导入、指定内核版本安装等仍需 CLI。此次没有把这些能力伪称为 Web 已实现。
3. 输入等待期间 CLI 使用状态快照，不持续后台刷新。其他入口改动后 `/status` 刷新；
   补全参数来自最近列表，应 `/node list`、`/sub list` 更新。
4. 真实平台只验证了已提供的 AES 订阅。Basic/Bearer/Token/age 的实现与回归测试存在，
   但没有对应真实平台凭据，不能宣称真实平台全通过。
5. 没有实际测试管理员 TUN 路由接管、远程 Web 暴露、局域网防火墙、速度/长时间耐久、
   Mac/Linux 运行及不同终端软件。六种目标完成交叉构建，不等同于六平台运行验收。
   浏览器请求 390 像素视口后实际仍为约 1009 像素，未把它记为窄屏验证通过。
   窄屏 CSS 已保留节点状态，但仍需真实窄视口验收。
6. 测试环境的后台服务必须具备外网权限；一次在受限环境重启后出现全失败，恢复联网
   条件后重测成功，该记录不作为订阅或应用故障结论。
7. 代码检查发现，内核版本安装/导入/切换与订阅操作没有统一的事务互斥；本轮以串行
   场景验收，没有证明多客户端并发版本操作安全。暂不建议多端同时安装或切换内核。
8. 亮色主题的代理地址卡片辅助文字对比度仍偏低；`/core status` 在停止/未安装时
   的“当前节点”字段实际是保存的选择。日常建议使用分层的 `/status`，这两处文案与
   视觉仍值得继续优化。

本次修改为 `/connect`、`/disconnect`、`/system-proxy status|on|off|recover`，并与 Web

### 发现的问题和改进建议

#### 1. Web 恢复与立即关闭存在可复现的时序问题（未修复）

复现命令：`web restart` 后立即 `shutdown`。

`web restart` 返回时 Web 已可用，但即时查询曾为 `core=starting`、端口未监听、系统代理
尚未接管。紧接着关闭两次均遇到：

```text
ProxyPilot: 停止代理内核: 订阅操作正在执行，请完成后再停止内核
```

原因由代码与实测共同确认：控制器先发布就绪，`Resume` 再通过后台 goroutine 恢复连接。
恢复与停止共用 `subscriptionAction` 互斥；StopCore 使用 TryLock，冲突便直接返回，错误
描述固定成“订阅操作”。它实际可能是启动恢复，并非用户确实正在更新订阅。

专项复测等待内核监听且系统接管后，关闭成功；自动恢复在该轮约需额外 0.24–0.28 秒，
不是可承诺的固定时长。短期使用方法是先 `/status` 确认服务运行与系统自动接入，再关闭。
建议产品增加恢复阶段提示，关闭时有界等待/取消恢复，并使用准确的冲突操作名称。

首轮生命周期中五条断言失败及专项中的一条即时就绪断言失败，主要是同一个问题的
表现和后果，并不代表存在六个独立缺陷。等待恢复后的原备份、关闭和重连断言通过。

#### 2. `--direct/--proxy` 会持久修改下载路径，反馈不够明显

从原直连订阅执行 `sub update/test ... --proxy` 后，持久配置的 `updateVia` 变为 proxy。
这符合当前实现和已有测试，不是下载路径失效，但用户可能误以为仅本次操作生效。

首轮“更新偏好不变”的测试断言因此失败：这是测试预期与当前语义不一致，不是凭据被
破坏。已使用 CLI `sub edit 1 --via direct` 恢复；后续测试增加 finally 恢复并核对配置。
建议成功信息明确说明“已保存为后续下载路径”，或者设计独立的临时路径参数。

#### 3. 长耗时检查及节点健康结论还可更清晰

`sub test` 本次一次耗时约 57 秒，返回“健康检查已完成”及总节点数，不直接给出通过/
失败/未检查数量。曾在切换路径后即时读取到尚无健康历史，后续专项复测则正常。
尚未进一步判定这一瞬时现象是否来自内核检查冷却、并发检查或重载，不能直接断言根因。

建议显示阶段进度、实际检查数量及完成时间，区分订阅下载成功、解密成功、加载成功和
节点可用。单个节点检查未通过也不应被描述为整个订阅无法下载。
