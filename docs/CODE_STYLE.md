# Kivo 代码规范

## 总体原则

1. 正确性、安全性、可恢复性优先于代码长度。
2. 平台差异必须封装在 `internal/platform`，业务层不得散落 `runtime.GOOS` 分支。
3. 代理内核差异必须封装在 `internal/core`，CLI 和 Web 层不得直接拼接 Mihomo 配置。
4. 所有配置变更均采用“生成临时文件 → 校验 → 原子替换 → 失败回滚”。
5. URL、Token、密码和控制密钥不得输出到日志；错误信息也必须经过脱敏。
6. HTTP 处理器只做参数校验和响应转换，业务逻辑统一进入 `app.Service`。

## Go 风格

- 必须通过 `gofmt` 与 `go vet`。
- 包名使用简短小写单词；导出标识符使用完整、明确的英文名称。
- 错误必须携带上下文，使用 `%w` 保留错误链。
- 网络、磁盘和进程操作必须接收 `context.Context` 或设置超时。
- 禁止无界 goroutine、无界日志、无超时 HTTP 请求。
- 除边界适配外，不使用 `panic` 表示业务错误。
- 接口由调用方定义，保持最小方法集。

## 注释规范

- 导出类型和复杂业务规则必须有中文注释。
- 注释解释“为什么”和约束，不逐行翻译代码。
- 安全敏感、跨平台差异、回滚逻辑必须写明风险。
- TODO 必须附带清晰原因，禁止只写 `TODO: fix`。

## HTTP API

- 路径统一以 `/api/v1` 开头。
- 成功响应统一为 `{ "data": ... }`。
- 失败响应统一为 `{ "error": { "code": "...", "message": "..." } }`。
- 批量操作失败可同时包含 `data`，必须保留逐项完成结果；未知统计使用可空值而非伪造 0。
- 长耗时安装可通过显式 `Accept: application/x-ndjson` 协商事件流；需逐条 Flush，包含错误与完成终止事件，断流不得当作成功。
- 配置了 Web Token 时，除健康检查外的所有 API 都必须验证 Bearer Token。
- 空 Token 是显式开放模式，界面与日志必须提示其风险；不得把“未初始化”误判成开放模式。

## Web 前端

- 不依赖 CDN，保证离线可用。
- 所有用户输入通过 DOM `textContent` 渲染，禁止拼接到 `innerHTML`。
- 页面必须支持键盘操作、窄屏和 `prefers-reduced-motion`。
- 危险操作必须二次确认，并给出可恢复性说明。
